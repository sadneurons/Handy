# Replacement dictionaries: design

Date: 2026-10-26. Branch base: `file-import`. Push target: `origin` only.

## Intent

The word-replacement list (merged from upstream PR #1533) is a single flat
list applied to every transcript. The owner dictates in several unrelated
contexts: clinical letters, creative writing, scientific writing. Each
needs its own exact-substitution vocabulary, and a clinical correction
applied to a short story is a defect. This design splits the flat list
into named dictionaries and lets the user choose which one is active.

## Goals

- Several named dictionaries of exact `from -> to` replacements.
- Exactly one dictionary (or none) is active at any time.
- The choice is always made by hand. Nothing infers the dictionary from
  content, window, time, or anything else.
- Two places to choose: before live dictation (glance at the overlay,
  switch via tray or settings if wrong) and at audio-file import (a
  selector on the import panel).
- Existing users lose nothing: the current flat list becomes a dictionary
  named "Clinical" on first launch after upgrade, and it is the active one.

## Non-goals

- Automatic or per-application dictionary switching.
- A prompt or modal when the recording shortcut fires.
- Changing the fuzzy `custom_words` list. It stays a single global list.
- Changing the replacement matching algorithm in `audio_toolkit/text.rs`.
- Syncing dictionaries between machines.

## Anti-goals

- Slowing down the start of recording. The shortcut must still start
  listening instantly.
- Any change that makes the upstream merge harder than it needs to be.
  Keep the diff confined to the settings model, one pipeline call site,
  the tray, the overlay, the import panel, and the Word Replacements UI.

## Constraints

- Tauri 2 app: Rust backend, React/TypeScript frontend, settings stored
  via `tauri-plugin-store` in `settings_store.json`. The owner runs only the
  latest build from this repo on the machine (the apt-installed Handy is
  retired once this ships), so no coexistence with an older binary is
  required. An older binary writing settings would drop the dictionaries,
  so the apt package must be removed or never launched after upgrading.
- Commands are exposed through `tauri-specta`; `src/bindings.ts` is
  regenerated by the dev build, never hand-edited.
- All UI strings go through i18next (`src/i18n/locales/en/translation.json`).
  Other locales may fall back to English.
- The tray menu is rebuilt from a snapshot (`MenuInputs` in `tray.rs`);
  new menu state must be added to that snapshot so the diffing still works.

## Data model (decided)

In `src-tauri/src/settings.rs`:

```rust
pub struct ReplacementDictionary {
    pub id: String,          // stable, e.g. uuid v4 string
    pub name: String,        // user-visible, editable
    pub entries: Vec<WordReplacement>,
}

// On AppSettings:
#[serde(default)]
pub replacement_dictionaries: Vec<ReplacementDictionary>,
#[serde(default)]
pub active_dictionary_id: Option<String>,   // None = no replacements applied
```

`WordReplacement { from, to }` is unchanged.

### Migration

On settings load, if the legacy `word_replacements` key is present and
non-empty and `replacement_dictionaries` is empty: create one dictionary
`{ id: new uuid, name: "Clinical", entries: <legacy list> }`, set it
active, write settings back, and drop the legacy key. If the legacy list is
empty or absent, start with an empty `replacement_dictionaries` and
`active_dictionary_id = None`. "Clinical" is the owner's request for their
own data; it is a one-time migration name and the user can rename it.

Note: `word_replacements` must stay declared in the struct (with
`#[serde(default)]`, marked deprecated) long enough to be read for
migration. After migration it is written back as an empty list.

## Pipeline (decided)

`managers/transcription.rs` currently calls
`apply_word_replacements(&corrected, &settings.word_replacements)`.
Replace with a helper on `AppSettings`:

```rust
pub fn active_replacements(&self) -> &[WordReplacement]
```

returning the active dictionary's entries or an empty slice. The file-import
path in `file_transcribe.rs` runs the same batch pipeline and therefore
picks this up automatically, except that import must be able to override
the active dictionary for that one job (see below).

### Per-job override (builder-check decision)

`TranscriptionManager::transcribe()` reads settings itself, so the import
override cannot be done at the single call site. Add an explicit selector
plumbed through `transcribe()` / `complete()` / `finish_text()`:

```rust
pub enum DictionarySelection {
    Global,              // whatever active_dictionary_id says
    None,                // apply no replacements
    Dictionary(String),  // this id, regardless of the global choice
}
```

Live dictation always passes `Global`. File import and the headless
`--transcribe-file` path pass whatever the user chose. Existing tests that
call `post_process_transcription_text(settings)` get the extra argument
with `Global`. This widens the diff slightly beyond the original anti-goal;
accepted, because the alternatives (temporarily rewriting the active id, or
applying the chosen dictionary after the fact) are either racy or produce
different output ordering.

## Choosing the dictionary (decided)

### Live dictation

- The recording overlay shows the active dictionary's name in small text
  (e.g. under the waveform). When none is active it shows nothing. The
  name is sent with the existing `show-overlay` event payload or read from
  settings when the overlay mounts; builder's choice, but it must reflect a
  change made while the overlay is hidden.
- The tray menu gets a "Dictionary" submenu, modelled on the existing model
  submenu: one `CheckMenuItem` per dictionary plus a "None" item. Picking
  one sets `active_dictionary_id` and triggers the normal settings-changed
  tray refresh.
- Settings UI: the Word Replacements panel gets a dictionary selector that
  also sets the active one (see UI below).
- CLI: `--dictionary <name-or-id>` sets the active dictionary on the running
  instance via the existing single-instance remote-control path, so a
  window-manager keybinding can switch context. Resolution is by exact id
  first, then case-insensitive name. Unknown values log a warning and
  change nothing. The switch persists like any other dictionary change.
  It combines with the other remote flags and is applied first, so
  `handy --dictionary creative --toggle-transcription` switches and then
  starts recording. The single-instance handler must therefore process
  `--dictionary` before its existing if/else chain rather than as another
  branch of it. The headless `--transcribe-file` path also honours
  `--dictionary`, passing `DictionarySelection::Dictionary(id)`.

### Audio-file import

`TranscribeFiles.tsx` (History page) gets a dictionary dropdown next to the
existing post-process toggle, defaulting to the currently active dictionary.
The `transcribe_files` command gains an optional `dictionary_id:
Option<String>` parameter. When `Some`, that dictionary's entries are used
for the job regardless of the global active one; when `None`, the global
active one is used. Choosing a dictionary in the import dropdown does not
change the global active dictionary.

The saved transcript header (`format_transcript`) gains a
`Dictionary: <name>` line (or `Dictionary: none`), and `HistoryEntry` gains
`dictionary_name: Option<String>` so History shows which vocabulary was
applied. This is my call, included because it is cheap and makes mistakes
visible. It is recorded for live dictation too, not only imports, since
the motivating mistake (clinical rules on a short story) happens in live
dictation; that means both `save_entry` calls in `actions.rs` are in
scope, plus a SQLite column migration in `history.rs`.

## Settings UI (decided in outline, details to builder)

The existing `WordReplacements.tsx` panel becomes:

- A row of tabs or a select across the top, one per dictionary, with an
  "Add dictionary" control. The selected tab is edited below using the
  existing from/to table.
- Per-dictionary actions: rename, delete (with confirm; deleting the active
  one sets active to None), import CSV, export CSV. CSV is two columns
  `from,to`, UTF-8, header row optional on import, written on export.
- A clearly separate "Active for dictation" control (radio or select) so
  that editing a dictionary and activating it are distinct actions.

New Tauri commands (replacing `update_word_replacements`):

- `update_replacement_dictionaries(Vec<ReplacementDictionary>)`
- `set_active_dictionary(Option<String>)`

Both go through `settings::write_settings` and emit the existing
settings-changed event so the tray and overlay refresh.

## Left to the builder

- Exact overlay placement and styling of the dictionary name.
- Whether the tray submenu label is "Dictionary" or the active name,
  following whatever the model submenu does.
- Tab vs. select in the settings panel. Pick what fits the existing
  Tailwind components.
- Test coverage: unit tests for migration (legacy non-empty, legacy empty,
  already migrated) and for `active_replacements`; a test for
  `--dictionary` resolution by id and by name.

## Acceptance

1. Fresh profile: no dictionaries, no replacements applied, overlay shows no
   dictionary name.
2. Upgrade from a profile with replacements: one "Clinical" dictionary,
   active, replacements still applied identically to before.
3. Create "Creative", switch to it from the tray; the overlay shows
   "Creative" on the next recording and clinical rules no longer fire.
4. Import an audio file with "Science" selected while "Clinical" is active:
   the transcript uses Science rules, the header says `Dictionary: Science`,
   and the tray still shows Clinical.
5. `handy --dictionary creative` from a shell switches the running instance.
